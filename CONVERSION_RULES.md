| A018 | **missing `;` terminators inferred** for T-SQL batches that run statements together — the single largest cause of skipped queries. Never splits: inside parens, after a continuation token (`,` `(` `+` `AND` `UNION` …), an `INSERT…SELECT` feed, a CTE body; the `;` lands on the last CODE line, skipping comment-only lines (`--OFFSET …` cannot swallow it) | anything the guards don't prove — refusal stays exactly as before |
| A019 | `UPDATE S … FROM templst S` / `DELETE S FROM templst S` → `UPDATE templst AS S …` / `DELETE FROM templst AS S`. LEFT/RIGHT/FULL/CROSS/APPLY/USING joins are still refused (L018). **v2.16.0, outer joins:** the FROM is kept as written and the target matched on its row id -- `UPDATE t AS S_upd SET … FROM t AS S LEFT JOIN x … WHERE S_upd.ctid = S.ctid AND (w)` (exact for tables and temp tables, not views); and `UPDATE t … FROM t JOIN …` with the target repeated UNALIASED ("table name specified more than once") is retargeted the same way. | FROM with joins (conditions must move to WHERE — a judgement call) → **L018** |
| A020 | **boolean columns used as VALUES** (A007 covers comparisons only). `COALESCE(IsX, 0/1/'0'/'1')` in ANY context → `FALSE/TRUE` default (else runtime 42804 `COALESCE types boolean and integer cannot be matched`); `CAST/CONVERT(<boolean> AS char type)` → `CASE … THEN '1' ELSE '0' END`, preserving T-SQL's `'1'/'0'` text — a plain cast yields `'true'/'false'` and silently breaks every consumer comparing to `'1'`. Same column evidence as A007. 721 instances in DropdownQueryMap alone, all in queries that had already passed grammar validation | column with no boolean evidence |
| A021 | **numeric CAST of a Dapper parameter → empty-string safe**: `CAST(@p AS INT)` → `CAST(NULLIF(CAST(@p AS TEXT), '') AS INT)`. The ACS guard idiom `@p = '' OR Id = TRY_CAST(@p AS INT)` breaks on PostgreSQL: `CAST('' AS INT)` raises 22P02 **at plan time** (bound parameter values are constant-folded), even when the other OR arm is true. `''` now yields NULL exactly like TRY_CAST. Runs after A015 | non-parameter operands; a non-numeric value still errors where TRY_CAST returned NULL (disclosed) |
| A022 | **`dbo.Split(x, sep)` table function → `STRING_TO_TABLE(x, sep) AS split(items)`** (PG14+). The MSSQL user-defined `dbo.Split` returns an `items` column; the PostgreSQL baseline has no such function (verified against the Liquibase changelogs), so the call fails at runtime with `function split does not exist`. Also catches the bare `SPLIT(...)` left behind by earlier conversions that only stripped `dbo.`. An existing table alias is preserved and given the `(items)` column | scalar (non-FROM) uses; arg counts other than 2 |
| A023 | **`STUFF((SELECT ', ' + x FROM … FOR XML PATH('')),1,n,'')` → `(SELECT STRING_AGG(x, ', ' [ORDER BY …]) FROM …)`.** TEXT-level, runs BEFORE the parse: sqlglot has no node for `FOR XML PATH`, so it emits SG-UNSUPPORTED and DROPS the option — which would leave a multi-row subquery where a scalar was meant. `SELECT DISTINCT` becomes `STRING_AGG(DISTINCT …)` and a trailing `ORDER BY` moves into the aggregate, which also makes the output deterministic where T-SQL's was not. Note the STUFF length argument is almost always `1` against a two-character separator (`', '`), so T-SQL left a stray leading space on every value; STRING_AGG has none — callers that split on `,` and trim are unaffected. Paren matching skips string literals, so `REPLACE(x, ')(', '')` inside the subquery cannot throw the depth count off | any STUFF that is not this idiom, incl. a genuine string edit with no FOR XML tail |
| A016 **extended** | now glues **four** shapes, not just UPDATE/SET: `UPDATE t`/`SET`, `INSERT INTO t (cols)`/`SELECT`, `CREATE [TEMP] TABLE x AS`/`SELECT`, and a **CTE's closing `)`**/`SELECT`. The ACS splitter cuts at ANY line whose first token is `SELECT INSERT UPDATE DELETE DROP CREATE ALTER IF SET DECLARE` and appends `
 ;` to the piece before it. The CTE case is the dangerous one — tearing there orphans the whole `WITH` clause, and every CTE-based hand conversion depends on the glue. Each pattern re-runs until it stops matching, because gluing one pair can expose another (a CTE chain closes several `)` in sequence). Guarded on the `)` line carrying no `;`, which distinguishes a CTE close from the end of the previous statement | — |
| — | **A007 SET-clause guard**: `SET IsRefundExpire = 'false'` is usually a VARCHAR payload, not a boolean (T-SQL BIT flags are set with 0/1) — sqlglot parses SET items as `EQ` nodes, and booleanising the string breaks the INSERT/UPDATE at runtime. In a SET clause only 0/1 integer literals count as boolean evidence; comparisons elsewhere keep the `'true'/'false'` handling | — |
| — | **A011 evidence extended (v2.6.0)**: a chain is text if any operand is a string literal, `ISNULL/COALESCE` with a textual argument, `CAST/CONVERT` to a char type, `CONCAT`/`UPPER`/`SUBSTRING`-class function, or a CASE with a textual branch. ## Resolvability rules (R001-R006 detail)

Grammar validation is an allowlist defined by PostgreSQL itself, so it catches unknown
unknowns -- but it only answers *is this syntactically PostgreSQL?*, never *will it resolve
at execution?*

```
OPENJSON(@x)   parses cleanly -- it is a legal function-call SHAPE.
               PostgreSQL then fails with
                   42883: function openjson(text) does not exist
```

Two converted constants shipped exactly that way and only surfaced when a user opened the
screen. **Grammar-valid is not runnable.** Every conversion now runs a third pass.

| Rule | Catches |
|---|---|
| R001 | Functions PostgreSQL does not have, which still PARSE: `OPENJSON`, `STRING_SPLIT`, `ISNULL`, `GETDATE`, `GETUTCDATE`, `DATEADD`, `DATEDIFF`, `DATEPART`, `DATENAME`, `CHARINDEX`, `LEN`, `STUFF`, `IIF`, `FORMAT`, `REPLICATE`, `SPACE`, `NEWID`, `TRY_CAST`, `TRY_CONVERT`, `SCOPE_IDENTITY`, `DATEFROMPARTS`, `EOMONTH`, plus `sys.time_zone_info`, `sp_executesql`, `dbo.` |
| R002 | Procedural control flow -- `IF`/`ELSE`, `BEGIN`...`END`, `SET @var`, `WHILE`, `MERGE`, `OUTPUT INSERTED`, `RAISERROR`, `BEGIN TRY`, `PIVOT`, `DECLARE @`. PostgreSQL has none of it outside a function body, so the constant is a REWRITE, not a substitution. Omitting these from the scan mis-sized 92 constants down to 23 in one sweep |
| R003 | Constructs that must NEVER be auto-converted: 3-arg `CONVERT(type, expr, style)` (the style code IS the date format -- 105 `dd-mm-yyyy`, 104 `dd.mm.yyyy`, 23 `yyyy-mm-dd`, 126 ISO8601), `CONVERT(bit, ...)`, and `SELECT TOP` (LIMIT moves to the END of the statement; wrong placement silently returns a DIFFERENT row) |
| R004 | `STUFF((SELECT ...))` -- the `FOR XML PATH` was stripped but its wrapper left, so the subquery now returns many rows: 21000 *more than one row returned by a subquery*. Rewrite as `STRING_AGG`; `STUFF` is then unnecessary |
| R005 | A `::json` cast inside a `CASE` branch. PostgreSQL constant-folds the unused branch when the value is a literal, so the CASE does NOT guard it and 22P02 still fires. Use `COALESCE(NULLIF(BTRIM(COALESCE(x,'')),''),'[]')::json` |
| R006 | `CREATE TEMP TABLE` with no `DROP TABLE IF EXISTS pg_temp.X` ahead of it. On a POOLED connection a mid-batch error leaves the table alive and every later call fails with *relation already exists* |

### Known false positives -- deliberately NOT reported

Reporting these wastes review time and invites someone to "fix" working code:

- Dapper list expansion `IN @Ids` -- legal at the Dapper layer (see v2.9.0)
- C# concatenation chains `@"..." + Const + @"..."` -- extract the whole chain first
- Deliberate **fragments** (`*_Preamble`, `*_Template`, `ColMap_*`, `DateFilter_*`) --
  `resolvability.is_probable_fragment()` recognises them; they are not standalone statements
- Function names appearing inside `--` / `/* */` comments, or inside string literals
- Functions PostgreSQL genuinely HAS: `LTRIM`, `RTRIM`, `BTRIM`, `UPPER`, `LOWER`,
  `SUBSTRING`, `REPLACE`, `COALESCE`, `NULLIF`, `CAST`, `ABS`, `ROUND`, `TRIM`

### Repair mode

A `dbms:postgresql` changeset whose body is still T-SQL is a conversion job,
not something to merely report — so repair mode rewrites it. The **id and
author are preserved**: the changeset is being fixed, not replaced, and
renaming it would make Liquibase treat it as new work and re-run it.

Safe because **a changeset that is invalid PostgreSQL cannot have run** —
Liquibase aborts on it, so no `DATABASECHANGELOG` row exists and there is no
stored checksum to break. Verify against `DATABASECHANGELOG` before deploying
anyway: a `dbo.`-flagged changeset would be valid if a `dbo` schema existed.

Only broken changesets are touched. A valid one is never rewritten, because
that *would* change a live checksum — the failure this whole exercise began
with. The repaired body passes the same two gates as generated SQL, and a
second pass over a repaired file is a no-op.

Repair does **not** fix LB007 (duplicate ids). Renaming the PostgreSQL half
makes Liquibase see new work and re-run it, which fails on a non-idempotent
body — that one needs `clear-checksums` or a human decision.

### The residual-T-SQL gate

pglast validates the PostgreSQL **grammar, not its semantics**. PostgreSQL
takes any unknown word as a type name, so `ADD c NVARCHAR(MAX)` parses cleanly
and fails only at execution with `type "nvarchar" does not exist`. Likewise
`WHERE IsDeleted = 0` parses and then raises
`operator does not exist: boolean = integer`.

So nothing is emitted unless the **assembled** text passes both gates: the
grammar check *and* `residual_tsql()` — NVARCHAR/UNIQUEIDENTIFIER/DATETIME/BIT,
`sys.*`, `dbo.`, `[brackets]`, `N''`, `@@vars`, `GO`, `sp_*`, T-SQL built-ins,
`IDENTITY(`, CLUSTERED, locking hints, and boolean-vs-0/1 comparisons (which
reuse A007's column-naming judgement so the two layers cannot drift).
`IF EXISTS (…) THEN` inside a `$$` block is exempt — that is ordinary PL/pgSQL.

Re-checking matters because `make_idempotent()` edits the engine's output
*after* the engine validated it.
